# Web-программирование. Лекция 13

## Авторизация: роли и защита управления новостями

[Предыдущая лекция: вход и выход](Web-программирование_Лекция_12_Аутентификация.md) · [Лабораторная №13](Лабораторная_работа_13_Авторизация.md)

## 1. Войти — не значит получить все права

Читатель библиотеки может брать книги, но не менять библиотечный каталог. Так же и пользователь сайта: подтверждённая личность не означает право редактировать общие новости.

В №12 мы отвечали на вопрос «Кто пришёл?». Теперь отвечаем: «Можно ли ему выполнить это действие?». Это авторизация.

К концу занятия вы сможете составить таблицу разрешений, закрыть административный обработчик и объяснить, почему API нуждается в тех же проверках.

## 2. Сначала записываем правила

| Действие | Гость | `user` | `admin` |
|---|---|---|---|
| Читать публичные новости и GET API | Да | Да | Да |
| Смотреть свой профиль | Нет | Да | Да |
| Открывать `admin.php` | Нет | Нет | Да |
| Добавлять, менять и удалять новости | Нет | Нет | Да |
| Добавлять и удалять новости через POST API | Нет | Нет | Да |

Гость — это отсутствие вошедшего пользователя, а не отдельная строка таблицы. `user` и `admin` — значения `users.role`. В API из №7 нет операции редактирования, поэтому не добавляем её незаметно в эту работу.

Такая таблица превращается в план проверки: для каждого действия пробуем все три состояния.

## 3. Запрет по умолчанию

Разрешаем административное действие только при точном совпадении роли:

```php
if ($user['role'] !== 'admin') {
    http_response_code(403);
    exit('Недостаточно прав.');
}
```

Не проверяем «роль не равна user, значит разрешить»: неизвестная роль тоже должна получить отказ. Новый пользователь всегда регистрируется с ролью `user`.

Права проверяем на сервере при каждом защищённом запросе. Это базовый принцип [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).

## 4. Где именно ставить проверку

В самом начале `admin.php`, до чтения параметров операции и любых INSERT, UPDATE, DELETE:

```php
require_once __DIR__ . '/access.php';
auth_require_admin();
```

Внутри POST-ветки, до изменения базы, проверяем CSRF. Только затем выполняется уже знакомый CRUD из №6.

Не достаточно защитить одну страницу с кнопками, если запись изменяет другой PHP-файл. Проверка нужна в том обработчике, который действительно работает с данными.

## 5. Три разные проверки

| Проверка | Вопрос |
|---|---|
| Сессия | Кто обратился? |
| Роль | Разрешено ли этому человеку действие? |
| CSRF | Есть ли правильный токен формы для этой сессии? |

CSRF-токен обычного пользователя не делает его администратором. Администратор тоже должен передать правильный токен. А идентификатор новости дополнительно проверяется как данные запроса.

Сервер принимает решение по сессии и записи в базе. Значения `role` и `user_id`, присланные клиентом, не являются доказательством прав.

## 6. Почему скрытая кнопка не защищает данные

Можно скрыть «Удалить» в интерфейсе, но запрос всё равно отправляется напрямую из другого клиента или консоли. Поэтому скрытие кнопки улучшает интерфейс, а серверная проверка защищает операцию.

Практический опыт: войдите обычным пользователем и откройте `admin.php` вручную. Если увидели управление, проверка отсутствует или стоит не там.

## 7. API — ещё одна дверь к той же таблице

В работе №7 `api-news.php` принимал JSON с операциями `create` и `delete`. Если закрыть только `admin.php`, API останется второй дверью к изменениям базы.

GET оставляем публичным. Перед POST проверяем пользователя, роль, токен, формат данных, затем выполняем SQL. Ответы API остаются JSON, а не HTML-страницей входа.

| Ответ | Значение в нашем API |
|---|---|
| 200 | Чтение или удаление выполнено |
| 201 | Новость создана |
| 401 | Требуется вход |
| 403 | Нет прав или неправильный CSRF-токен |
| 405 | Метод не поддерживается |
| 415 | Нужен `application/json` |
| 422 | Данные формы не прошли проверку |

HTML-страницу гостю можно перенаправить на вход. API возвращает 401: клиентский JavaScript сам покажет сообщение пользователю.

## 8. Как передать CSRF через fetch

В обычной форме токен передаётся скрытым полем. При JSON-запросе используем заголовок `X-CSRF-Token`.

В нашей схеме успешный GET API возвращает новости и токен, только если текущий посетитель — администратор. JavaScript сохраняет токен в переменной и прикладывает к POST. В PHP он доступен как `$_SERVER['HTTP_X_CSRF_TOKEN']`.

Это взаимодействие внутри одного origin — одинаковых схемы, хоста и порта. Открывайте интерфейс через тот же локальный сервер. Cookie передаётся в same-origin fetch; отдельно разрешать CORS здесь не требуется. Не добавляйте произвольный межсайтовый доступ к ответам с токеном.

Токен не кладём в URL и не сохраняем в `localStorage`. После нового входа обновляем список и получаем актуальный токен. Такой подход к передаче токена описан в [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## 9. Как назначить администратора

Для лабораторной сначала регистрируем две отдельные учётные записи. Затем преподаватель или владелец локальной базы меняет роль одной записи через phpMyAdmin. Проверяем email и число изменённых строк. Публичную кнопку повышения роли не создаём.

Роль читается из базы при каждом запросе. Если вернуть администратору `user`, следующий административный запрос должен получить отказ без повторного входа.

## 10. Проверяем запреты, а не только успех

Проверка «администратор удалил новость» покрывает только разрешённый путь. Нужны также попытки гостя, обычного пользователя и администратора без токена.

Для запрещённого действия проверяем два результата одновременно: HTTP-отказ и отсутствие изменения в таблице. Один текст «Ошибка» не доказывает, что INSERT не был выполнен раньше.

## 11. Где заканчивается эта модель

В работе только общие новости и две роли. Если появится правило «автор редактирует только свою новость», одной роли будет недостаточно: понадобится поле автора и проверка принадлежности конкретной записи. Это отдельное расширение.

Права не заменяют валидацию, параметры PDO и экранирование. Администратор тоже может ошибиться во вводе. Пример остаётся локальным учебным приложением; ограничения публичного входа перечислены в лекции №12.

## 12. Проверьте себя

1. Пользователь вошёл и получил CSRF-токен. Достаточно ли этого для удаления новости?
2. Что случится, если защитить только `admin.php`, оставив старый API?
3. Чем ответ API для гостя отличается от ответа для вошедшего пользователя без прав?
4. Откуда берём роль при проверке?
5. Почему после запроса с отказом нужно посмотреть базу?

Ответы: нет, нужна роль `admin`; останется обход ограничений через API; 401 и 403 соответственно; из базы по серверному идентификатору сессии; чтобы убедиться, что данные не изменились до отказа.
