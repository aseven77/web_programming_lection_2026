# Web-программирование. Лекция 10

## Сессии PHP: как сайт запоминает список «Прочитать позже»

[← Лекция 9: пагинация](Web-программирование_Лекция_9_Пагинация.md) · [Лабораторная работа №10](Лабораторная_работа_10_Сессии.md)

## 1. Какую задачу решаем

На сайте уже есть новости, и мы умеем показывать их частями. Теперь посетитель нашёл интересную новость, но не успевает её прочитать. Ему нужна кнопка **«Прочитать позже»**.

После нажатия возле новости появится отметка. Посетитель обновит страницу — отметка останется. В другом профиле браузера будет свой список.

Сегодня изучаем одну новую идею: **сервер может запоминать небольшой набор данных между запросами одного браузера**. Для этого используем сессию PHP.

Создадим `reading-list.php`: все новости небольшого учебного набора и отметки выбранных. Поиск и пагинация остаются в файлах прошлых работ.

После занятия вы сможете объяснить, где находится список, зачем браузеру cookie и почему добавление отметки не требует команды `INSERT` в таблицу `news`.

## 2. Почему обычная переменная не помогает

Представим такой код:

```php
<?php
$selected = [];
$selected[5] = true;
```

Во время этого запуска PHP знает, что выбрана новость №5. Но при следующем запросе файл запускается заново. Обычные переменные предыдущего запуска не превращаются автоматически в память сайта.

Это похоже на черновик: человек решил задачу, а для следующего посетителя взял новый листок. Если нужно что-то помнить, потребуется отдельное место хранения.

**Пауза для проверки.** Сохранится ли обычная переменная `$selected` сама по себе после нового запроса? Нет. Нужно явно сохранить сведения, например в сессии или базе данных.

## 3. Сессия и cookie: гардероб и номерок

Представьте гардероб:

- Вещи лежат в гардеробе. Это данные сессии **на сервере**.
- У посетителя есть номерок. Это идентификатор сессии **в cookie браузера**.
- Посетитель показывает номерок, и гардеробщик находит нужные вещи. Браузер отправляет cookie, и PHP загружает соответствующую сессию.

Cookie — небольшое значение, которое браузер хранит для сайта и отправляет с подходящими запросами. В нашей работе cookie хранит идентификатор сессии, а сам список новостей остаётся на сервере. Так устроен обычный режим сессий PHP с cookie. [PHP Manual: основы сессий](https://www.php.net/manual/en/session.examples.basic.php).

Путь одного нажатия:

```text
Браузер: «Добавь новость №5», плюс cookie с номером сессии
                     ↓
PHP: открывает нужную сессию и запоминает номер 5
                     ↓
Браузер: снова открывает страницу
                     ↓
PHP: читает ту же сессию и показывает отметку возле новости №5
```

Номерок не сообщает имя человека. В работе нет аккаунта, пароля или проверки личности. Сессия связывает запросы с одним хранилищем; сама по себе она не даёт прав редактировать новости.

## 4. Три места хранения — три разные задачи

| Что храним | Где храним | Зачем |
|---|---|---|
| Заголовок и текст новости | В таблице `site.news` | Общие новости сайта |
| Номера выбранных новостей | В сессии на сервере | Выбор этого браузера |
| Идентификатор сессии | В cookie браузера | Найти нужную сессию |

Допустим, новость №5 называется «Открытие выставки». В сессию достаточно положить номер `5`. Название и текст по-прежнему читаем из базы.

Если заголовок изменился, увидим актуальное название из таблицы. База отвечает на вопрос «Какие новости существуют?», а сессия — «Какие из них выбраны здесь?».

В нашем массиве `reading_list` будут только идентификаторы как ключи и отметки `true` как значения. Отдельно сессия будет хранить технический токен формы и короткое сообщение о результате.

## 5. Как начать работу с сессией

```php
<?php
session_start();

if (!isset($_SESSION['reading_list'])) {
    $_SESSION['reading_list'] = [];
}
```

Разберём по строчке:

- `session_start()` открывает существующую сессию или начинает новую.
- `$_SESSION` — специальный массив PHP для данных этой сессии.
- `['reading_list']` — название нашей ячейки. Его придумали мы.
- `isset(...)` проверяет, есть ли значение и не равно ли оно `null`.
- `!` означает «не». Поэтому `!isset(...)` читается как «если ячейки ещё нет».
- `[]` — пустой массив: ни одной новости пока не выбрано.

Условие здесь необходимо. Если на каждом запросе без условия выполнять `$_SESSION['reading_list'] = [];`, мы сами будем стирать выбор при обновлении страницы.

`session_start()` вызываем **до HTML, `echo` и любого другого вывода**, потому что PHP может отправлять заголовки с cookie. Начало файла — сразу `<?php`, без пробелов перед ним. [PHP Manual: session_start](https://www.php.net/manual/en/function.session-start.php).

В лабораторной добавим ещё проверку `is_array(...)`: она помогает восстановить пустой список, если при прошлых экспериментах в эту ячейку записали, например, строку.

## 6. Добавить, проверить и убрать отметку

Используем массив, в котором **ключ — номер новости**:

```php
$_SESSION['reading_list'][5] = true;
$_SESSION['reading_list'][12] = true;
```

Мысленно это можно прочитать так:

```text
Новость 5  → выбрана
Новость 12 → выбрана
```

`true` означает «да». Нам не важна позиция новости в списке; важно, выбран ли конкретный номер.

Повторное выполнение `$_SESSION['reading_list'][5] = true;` снова записывает значение в ту же ячейку. Второй копии новости №5 не появляется. Это полезное свойство: повторный запрос не увеличивает список.

Проверим отметку:

```php
if (isset($_SESSION['reading_list'][5])) {
    echo 'Новость уже отложена';
}
```

Уберём отметку:

```php
unset($_SESSION['reading_list'][5]);
```

`unset(...)` удаляет указанную ячейку. В этой строке удаляется только выбор новости №5. Сама новость в таблице остаётся, выбор других новостей тоже остаётся.

Количество отметок можно получить так:

```php
$count = count($_SESSION['reading_list']);
```

**Проверьте себя:** добавили №5, ещё раз №5, затем №12. Сколько отметок? Две: ключи `5` и `12`.

## 7. Как кнопка сообщает серверу номер новости

В каждой карточке будет обычная HTML-форма:

```html
<form action="reading-list.php" method="post">
    <input type="hidden" name="id" value="5">
    <!-- В готовой форме будет также скрытое поле csrf. -->
    <button name="action" value="add">Прочитать позже</button>
    <button name="action" value="remove">Убрать отметку</button>
</form>
```

Это схема формы, не готовая защищённая версия. Полный вариант соберём в лабораторной.

Скрытое поле `id` передаёт номер новости. Нажатая кнопка передаёт своё значение `action`: `add` или `remove`. Слово `action` в поле — выбранное нами имя операции; атрибут `action="reading-list.php"` у формы — адрес отправки.

Используем POST, потому что меняем выбор посетителя. GET оставляем для просмотра. При открытии ссылки `reading-list.php?id=5&action=add` обработчик не должен добавлять отметку.

Скрытое поле не является защитой: его можно изменить через инструменты браузера. Сервер обязан проверить данные так же внимательно, как обычный текстовый ввод.

## 8. Три проверки перед изменением списка

В библиотеку принесли записку «Отложите книгу №5». Прежде чем выполнять просьбу, сотрудник проверит: понятна ли операция, правильно ли написан номер, существует ли книга.

Наш PHP делает то же самое:

1. `action` должен быть строкой `add` или `remove`.
2. `id` должен быть целым положительным числом.
3. Новость с этим номером должна существовать в прочитанной таблице.

Число `999999` может быть правильным по форме, но отсутствовать в базе. Поэтому «это число» и «такая новость существует» — разные проверки.

Выражение `$_POST['id'] ?? ''` читается как «возьми поле `id`, а если его нет или оно равно `null`, возьми пустую строку». Значок `??` задаёт запасное значение. Он не проверяет тип и не делает данные безопасными.

`is_string(...)` проверяет, что пришла строка. Это нужно, потому что запрос может содержать `id[]=5`: тогда PHP получит массив, хотя форма ожидала одно значение.

Проверку числа сделаем через `filter_var(..., FILTER_VALIDATE_INT, ['options' => ['min_range' => 1]])`. Она вернёт целое число при успехе и `false` при неудаче. Запись `=== false` проверяет именно неудачу проверки, без преобразования типов.

## 9. Небольшой защитный шаг: токен формы

Одна проверка номера не защищает от чужой страницы, которая пытается отправить запрос на наш сайт через браузер посетителя. Браузер в определённых условиях прикладывает cookie автоматически. Такой вид подделки запроса называют **CSRF**.

Поэтому сервер создаёт случайный токен, сохраняет его в сессии и вставляет в скрытое поле своей формы. При POST он сравнивает присланный токен с сохранённым. Если токена нет или он неправильный, выбор не меняется. [OWASP: токен, связанный с сессией](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#synchronizer-token-pattern).

Токен похож на случайный контрольный код бланка. Запрос приносит его вместе с номером новости. Это отдельный код, **не идентификатор сессии** и не пароль.

```php
$_SESSION['reading_csrf'] = bin2hex(random_bytes(32));
```

`random_bytes(32)` создаёт 32 случайных байта. `bin2hex(...)` превращает их в строку из 64 символов, которую удобно передать в HTML. Эту строку создаём один раз для сессии, а не заново перед каждой проверкой. [PHP Manual: random_bytes](https://www.php.net/manual/en/function.random-bytes.php).

Для сравнения применяем `hash_equals($savedToken, $sentToken)`: первым передаём сохранённый сервером токен, вторым — строку из запроса. Функция предназначена для сравнения таких секретных строк. Перед вызовом проверяем `is_string($sentToken)`. [PHP Manual: hash_equals](https://www.php.net/manual/en/function.hash-equals.php).

Токен не заменяет проверку `id`, экранирование HTML или проверку прав доступа. В этой работе он решает только задачу защиты изменяющих запросов от CSRF.

## 10. Зачем после POST снова открывать страницу

После успешного изменения отправим:

```php
header('Location: reading-list.php', true, 303);
exit;
```

`header(...)` отправляет HTTP-заголовок. `Location` указывает адрес перехода, `303` предлагает получить страницу по GET после выполненного POST. `exit` останавливает текущий PHP-скрипт: после перенаправления больше ничего не выполняем. [PHP Manual: header](https://www.php.net/manual/en/function.header.php).

Эту последовательность называют **Post/Redirect/Get**, сокращённо PRG:

```text
POST: изменить выбор → 303: перейти к списку → GET: показать список
```

После перехода обновление страницы повторяет просмотр, а не отправку формы. При ошибке проверки остаёмся на странице с понятным сообщением; успешное изменение и ошибочный запрос — разные случаи.

Сообщение «Добавлено в список» можно передать через сессию: записать перед переходом, прочитать при GET и сразу убрать `unset(...)`. Тогда оно покажется один раз, а не будет появляться после каждого обновления.

## 11. Что произойдёт в другой вкладке и инкогнито

Две обычные вкладки одного профиля браузера обычно используют одни и те же cookie этого сайта. Поэтому после обновления обе покажут одинаковые отметки.

Другой профиль или отдельный режим инкогнито использует другое хранилище cookie. Он получит другую сессию и начнёт со своего списка. Несколько окон внутри одного сеанса инкогнито могут разделять cookie между собой; для проверки достаточно сравнить обычное окно и инкогнито.

Закрытие одной вкладки **не означает очистку сессии**. У cookie есть свои правила срока действия, у данных на сервере — свои правила очистки. При стандартном `session.cookie_lifetime = 0` cookie является сеансовым; некоторые браузеры умеют восстанавливать такие cookie вместе с восстановлением окон. Поэтому нельзя обещать исчезновение списка в определённую секунду после закрытия браузера. [PHP Manual: настройки сессий](https://www.php.net/manual/en/session.configuration.php), [MDN: срок действия cookie и восстановление сеанса](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#expiresdate_optional).

Наш список подходит для учебного временного выбора. Для постоянного списка, который доступен на разных устройствах после входа, потребуются аккаунты и хранение выбора в базе. Это отдельная задача.

## 12. Частые ошибки и их смысл

| Что получилось | Возможная причина | Что проверить |
|---|---|---|
| Выбор исчезает при обновлении | Массив обнуляется на каждом запросе | Создание пустого списка должно быть внутри условия |
| `Headers already sent` | Вывод начался раньше заголовков | Пробелы, BOM, HTML и `echo` до `session_start()` или `header()` |
| Вкладки показывают одинаковый выбор | У них общая сессия | Для отдельного выбора открыть другой профиль или инкогнито |
| При удалении исчезла новость из базы | Выполнен `DELETE` из старой работы | Здесь требуется только `unset(...)` для отметки |
| Любое нажатие даёт ошибку токена | Токен каждый раз заменяется или не отправляется | Создавать его один раз; проверить `name="csrf"` |

## 13. Вопросы с короткими ответами

**Где хранится текст новости?** В таблице `news`. В списке выбора храним её номер.

**Где хранится массив `$_SESSION['reading_list']` между запросами?** На сервере. Браузер обычно хранит идентификатор сессии в cookie.

**Чем `unset($_SESSION['reading_list'][5])` отличается от `DELETE FROM news WHERE id = 5`?** Первая команда убирает личную отметку. Вторая удаляет общую новость из базы.

**Почему повторное добавление не создаёт дубль?** Мы снова записываем `true` по тому же ключу `5`.

**Достаточно ли скрыть `id` в форме?** Нет. Скрытое поле можно подменить, поэтому сервер проверяет тип, число и существование новости.

**Что делает CSRF-токен?** Позволяет серверу отклонить изменяющий запрос без правильного токена данной сессии. Он не определяет личность посетителя.

**Что обновится после успешного POST и перехода 303, если нажать F5?** Страница списка будет снова запрошена по GET.

**Можно ли гарантировать, что список исчезнет после закрытия вкладки?** Нет. Вкладка, cookie и серверная сессия имеют разные сроки жизни.
