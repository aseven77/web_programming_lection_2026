# Web-программирование. Лекция 1

## Современная архитектура веб-приложений и технологии их создания

---

## 1. От статичных страниц к современным веб-приложениям

Первые сайты представляли собой статичные HTML-документы: сервер отдавал один и тот же файл каждому посетителю, а взаимодействие с пользователем сводилось к переходам по ссылкам.

Современный сайт или сервис — это полноценное **интерактивное приложение**: личный кабинет, интернет-магазин, мессенджер, панель аналитики. Такие приложения обмениваются данными с сервером асинхронно, обновляют интерфейс без перезагрузки страницы и по возможностям приближаются к нативным программам.

Технологии для разработки веб-приложений принято делить по площадке исполнения:

| Сторона | Что выполняется | Основные технологии сегодня |
|---|---|---|
| **Frontend** (клиент) | Код выполняется в браузере пользователя | HTML, CSS, JavaScript/TypeScript, Vue, React, Svelte |
| **Backend** (сервер) | Код выполняется на удалённом сервере | Node.js, PHP (Laravel), Python (Django/FastAPI), Go, Java/Kotlin (Spring), C# (.NET) |

## 2. Клиент-серверная архитектура

**Клиент-сервер** — архитектура, при которой нагрузка распределена между **серверами** (поставщиками услуг) и **клиентами** (потребителями услуг). Клиент и сервер обмениваются данными по сети, чаще всего по протоколу **HTTP/HTTPS**.

**Web-сервер** — программа (или компьютер, на котором она работает), принимающая HTTP-запросы от клиентов (обычно браузеров) и отправляющая в ответ HTML-страницы, JSON-данные, файлы, медиапотоки и т. д. Сегодня один и тот же сервер чаще всего отдаёт не готовый HTML, а данные в формате **JSON** — представлением этих данных занимается уже клиентское приложение.

Типичный цикл обработки запроса:

1. Пользователь взаимодействует с интерфейсом (переход по ссылке, клик по кнопке, отправка формы).
2. Браузер устанавливает соединение с сервером и отправляет HTTP-запрос.
3. Запрос попадает на сервер — напрямую или через **балансировщик нагрузки** / **API Gateway**, если серверов несколько.
4. Backend-приложение обрабатывает запрос, при необходимости обращается к базе данных, кэшу или другим сервисам.
5. Сервер формирует ответ (чаще всего JSON) и отправляет его клиенту.
6. Клиентское приложение обновляет интерфейс без перезагрузки страницы.

## 3. Модель сети TCP/IP

Передача данных между клиентом и сервером описывается многоуровневой моделью. Наиболее распространена упрощённая **5-уровневая модель TCP/IP** (полная — 7-уровневая модель OSI):

| Уровень | Назначение | Примеры протоколов |
|---|---|---|
| 5. Прикладной | Интерфейс для приложений и пользователя | HTTP/HTTPS, WebSocket, FTP, SMTP, SSH |
| 4. Транспортный | Доставка данных между приложениями, порты | TCP, UDP, QUIC |
| 3. Сетевой | Адресация и маршрутизация между сетями | IP (IPv4, IPv6) |
| 2. Канальный | Соединение устройств внутри локальной сети, MAC-адреса | Ethernet, Wi-Fi |
| 1. Физический | Передача сигналов по физической среде | оптоволокно, радиоканал, витая пара |

Важные изменения последних лет:

- **IPv6** постепенно вытесняет IPv4 — свободный пул адресов IPv4 исчерпан ещё в 2019–2020 годах, и провайдеры всё активнее переходят на IPv6.
- На транспортном уровне рядом с TCP и UDP закрепился протокол **QUIC** (лежит в основе HTTP/3) — он совмещает надёжность TCP со скоростью UDP.
- На прикладном уровне для realtime-взаимодействия (чаты, уведомления, онлайн-игры) используется **WebSocket**, обеспечивающий постоянное двустороннее соединение поверх TCP.

## 4. Типы современных веб-приложений

Единой строгой классификации не существует, но чаще всего выделяют следующие подходы к построению фронтенда:

### MPA — Multi Page Application
Классическая модель: каждая навигация — это новый запрос к серверу и полная перезагрузка страницы. Хорошо индексируется поисковиками «из коробки», подходит для контентных сайтов и крупных каталогов.

### SPA — Single Page Application
Приложение загружается один раз, а дальнейшее взаимодействие происходит без перезагрузки страницы: JavaScript-фреймворк динамически подменяет содержимое, обращаясь к серверу через API. Строится на фреймворках **Vue**, **React**, **Angular**, **Svelte**.

### SSR — Server-Side Rendering
Компромисс между MPA и SPA: HTML для первого экрана генерируется на сервере (быстрая отдача контента, хорошее SEO), а дальнейшая навигация работает как в SPA. Реализуется фреймворками **Nuxt** (для Vue), **Next.js** (для React), **SvelteKit**.

### SSG — Static Site Generation
HTML-страницы генерируются заранее, на этапе сборки проекта, и раздаются как статические файлы через CDN — максимальная скорость загрузки. Подходит для блогов, документации, лендингов (Nuxt Content, Astro, Next.js в режиме SSG).

### PWA — Progressive Web Application
Веб-приложение, которое можно «установить» на устройство: работает офлайн благодаря Service Worker, поддерживает push-уведомления, не требует магазинов приложений. Границы между PWA и нативным приложением продолжают стираться.

**Сравнение подходов:**

| Подход | Плюсы | Минусы |
|---|---|---|
| MPA | Простое SEO, привычная навигация | Каждый переход — перезагрузка, больше нагрузки на сервер |
| SPA | Высокая скорость взаимодействия после загрузки | Требует JS для рендера, сложнее с SEO без доп. мер |
| SSR | Быстрый первый экран + хорошее SEO | Сложнее в разработке и хостинге, нагрузка на сервер при рендере |
| SSG | Максимальная скорость отдачи, дешёвый хостинг | Не подходит для часто меняющихся данных без пересборки |
| PWA | Офлайн-режим, push-уведомления, «установка» без сторов | Ограничения на iOS, поддерживается не всеми браузерами полностью |

## 5. Компоненты современного веб-приложения

### 5.1 Frontend
Визуальная часть, которую видит и с которой взаимодействует пользователь. Сегодня фронтенд — это не просто HTML/CSS/JS, а полноценная инженерная экосистема:

- **Фреймворки:** Vue 3 (Composition API), React, Angular, Svelte.
- **Сборщики и dev-инструменты:** Vite, Webpack, esbuild.
- **Управление состоянием:** Pinia (Vue), Redux/Zustand (React).
- **Типизация:** TypeScript — фактический стандарт для средних и крупных проектов.
- **Стилизация:** Tailwind CSS, CSS-модули, компонентные UI-библиотеки.

### 5.2 Backend
Логика, работающая на сервере и недоступная пользователю напрямую. Клиент обращается к ней через **API**.

- **Языки и среды выполнения:** Node.js, Python, PHP, Go, Java/Kotlin, C#.
- **Фреймворки:** Express/NestJS (Node.js), Laravel (PHP), Django/FastAPI (Python), Spring Boot (Java).
- **Базы данных:** реляционные — PostgreSQL, MySQL; нереляционные — MongoDB, Redis (кэш и очереди).
- **Веб-серверы и прокси:** Nginx, часто как обратный прокси и балансировщик перед приложением.

### 5.3 Способы обмена данными между клиентом и сервером (API)

| Подход | Особенности | Где применяется |
|---|---|---|
| **REST API** | Ресурсы адресуются URL, методы HTTP задают действие, данные — обычно в JSON | Стандарт де-факто для большинства веб-сервисов |
| **GraphQL** | Клиент сам описывает, какие поля данных ему нужны, один эндпоинт | Сложные интерфейсы с гибкими запросами данных |
| **WebSocket** | Постоянное двустороннее соединение | Чаты, уведомления в реальном времени, онлайн-игры |
| **gRPC** | Бинарный протокол поверх HTTP/2, строгая контрактная схема | Взаимодействие между микросервисами |

## 6. HTTP-протокол

**HTTP (HyperText Transfer Protocol)** — протокол прикладного уровня, лежащий в основе обмена данными между клиентом и сервером в вебе. Сегодня повсеместно используется его защищённая версия — **HTTPS**, в которой данные шифруются по протоколу TLS, что защищает их от перехвата и подмены.

### Версии HTTP

| Версия | Год | Особенности |
|---|---|---|
| HTTP/1.1 | 1997 | Постоянные соединения (keep-alive), базовый стандарт долгие годы |
| HTTP/2 | 2015 | Мультиплексирование запросов в одном соединении, бинарный формат, сжатие заголовков |
| HTTP/3 | 2022 (стандартизирован RFC 9114) | Работает поверх протокола **QUIC** (UDP) вместо TCP — устраняет задержки при потере пакетов, ускоряет установку соединения |

### Структура HTTP-сообщения

HTTP-запрос и HTTP-ответ имеют одинаковую структуру:

1. **Стартовая строка** — метод, адрес ресурса и версия протокола (запрос) или код состояния (ответ).
2. **Заголовки (Headers)** — метаданные: тип содержимого, авторизация, кэширование и т. д.
3. **Тело сообщения (Body)** — опционально; в запросах чаще всего JSON, в ответах — JSON, HTML, файл.

### Основные методы (глаголы) HTTP

| Метод | Назначение |
|---|---|
| GET | Получение данных без изменения состояния сервера |
| POST | Создание нового ресурса / отправка данных |
| PUT | Полная замена существующего ресурса |
| PATCH | Частичное обновление ресурса |
| DELETE | Удаление ресурса |
| HEAD | Как GET, но без тела ответа — для проверки заголовков |
| OPTIONS | Запрос доступных методов для ресурса, используется в CORS-preflight |

### Коды состояния ответа

| Класс | Значение | Примеры |
|---|---|---|
| 1xx | Информационные | 100 Continue |
| 2xx | Успех | 200 OK, 201 Created, 204 No Content |
| 3xx | Перенаправление | 301 Moved Permanently, 304 Not Modified |
| 4xx | Ошибка клиента | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests |
| 5xx | Ошибка сервера | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable |

### Пример REST-запроса и ответа

```http
GET /api/weather?city=moscow HTTP/1.1
Host: api.example.com
Accept: application/json
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "city": "Moscow",
  "temperature": 5,
  "condition": "cloudy"
}
```

Пример POST-запроса на создание ресурса:

```http
POST /api/pets HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "name": "Барсик",
  "status": "available"
}
```

## 7. Аутентификация и безопасность

В отличие от старых сессионных подходов, современные веб-приложения чаще всего используют:

- **JWT (JSON Web Token)** — самодостаточный токен, который клиент передаёт в заголовке `Authorization: Bearer <token>` при каждом запросе; не требует хранения сессии на сервере.
- **OAuth 2.0 / OpenID Connect** — стандарт для входа через сторонние сервисы (Google, GitHub и т. п.) и выдачи ограниченных прав доступа.
- **CORS (Cross-Origin Resource Sharing)** — механизм, разрешающий или запрещающий браузеру выполнять запросы к серверу с другого домена.
- **HTTPS + TLS** — обязательный стандарт: браузеры маркируют HTTP-сайты как небезопасные.

## 8. Современная серверная инфраструктура

Технологии организации серверной части существенно изменились по сравнению с эпохой CGI-скриптов и расширений веб-сервера:

- **Микросервисная архитектура** — приложение разбивается на независимые сервисы, каждый отвечает за свою область (заказы, оплата, пользователи) и общается с другими через API или очереди сообщений.
- **Контейнеризация** — приложения упаковываются в **Docker**-контейнеры для одинакового поведения в любой среде; управление множеством контейнеров берёт на себя **Kubernetes**.
- **Serverless / Function as a Service** — код выполняется по запросу в облаке (AWS Lambda, Vercel Functions, Cloudflare Workers) без необходимости администрировать сервер.
- **CI/CD** — автоматическая сборка, тестирование и развёртывание приложения при каждом изменении кода (GitHub Actions, GitLab CI).
- **Обратный прокси и балансировка** — Nginx, Traefik принимают внешние запросы и распределяют их между экземплярами приложения.

## 9. Итоги

1. Современное веб-приложение строится на чётком разделении **frontend** (Vue, React, TypeScript) и **backend** (Node.js, Python, PHP, Go), общающихся через **API** — чаще всего REST или GraphQL.
2. Обмен данными идёт по протоколу **HTTP/HTTPS**; актуальная версия — **HTTP/3** поверх QUIC, повышающая скорость и надёжность соединения.
3. Веб-приложения строятся по разным архитектурным подходам — **MPA, SPA, SSR, SSG, PWA** — выбор зависит от требований к SEO, скорости и офлайн-работе.
4. Безопасность обеспечивается связкой **HTTPS + TLS**, а авторизация — токенами **JWT** и протоколом **OAuth 2.0**.
5. Серверная инфраструктура опирается на **контейнеризацию**, **микросервисы** и **CI/CD**, что заменило устаревшие подходы вроде CGI-скриптов и расширений веб-сервера (ISAPI/NSAPI).
