Web-программирование. Лекция 14

Git с нуля: как сохранять историю своего сайта

Предыдущая лекция: авторизация · Лабораторная №14

Здесь можно начинать с нуля. Не нужно заранее знать команды, английские слова или GitHub. Каждое новое слово разберём на примере маленького сайта.

Цель: научиться сохранять понятные версии проекта, видеть изменения и пробовать новую идею в отдельной ветке.

Как проходить: сначала разделы 1–12 и первые девять шагов лабораторной. Затем ветки и оставшаяся практика. GitHub в конце — дополнительное знакомство, аккаунт для основной работы не нужен.

1. Знакомая история: «Где моя рабочая версия?»

Представьте, что вы делаете сайт о своём питомце. В понедельник добавили заголовок. Во вторник — фотографию. В среду поменяли оформление, и всё стало некрасиво.

Хочется вернуть вариант вторника. Но файл уже сохранён! Тогда начинаются папки:

сайт
сайт_новый
сайт_точно_новый
сайт_последний_рабочий

Через неделю трудно вспомнить, где что лежит и чем варианты отличаются.

Git — программа, которая помогает вести историю изменений проекта. Вы отмечаете важные моменты, а потом можете посмотреть, что меняли, и достать нужную сохранённую версию.

Похоже на сохранения в игре: прошли важное место — сделали сохранение с понятной подписью. Но Git не делает такие сохранения за вас автоматически: нужный момент выбираете вы.

Вопрос: если изменить файл и не сохранить его ни в редакторе, ни в Git, будет ли Git знать новый текст? Нет. Сначала файл нужно сохранить на диск.

2. Три вещи, которые легко перепутать

Что Простое объяснение Пример
Редактор кода Место, где мы пишем файлы Visual Studio Code
Git Программа, которая хранит историю проекта Работает на нашем компьютере
GitHub Сервис, где можно разместить Git-репозиторий и работать вместе Открывается в браузере

Git и GitHub — разные вещи. Можно пользоваться Git без GitHub и без интернета. Для первого занятия достаточно установленного Git, редактора и браузера.

Сохранить файл в редакторе, записать версию в Git и отправить её на GitHub — три отдельных действия. Одно не запускает остальные автоматически.

История только на одном компьютере не спасает от поломки диска. Для этого нужна отдельная копия, например на другом устройстве или в удалённом репозитории.

3. Куда вообще вводить команды

Терминал — окно, в котором мы даём компьютеру текстовые инструкции. Команда — одна такая инструкция.

В Windows будем использовать PowerShell. В VS Code откройте папку проекта через «Файл → Открыть папку», затем выберите «Терминал → Создать терминал». В списке терминалов выберите PowerShell, если открыт другой вариант.

Можно работать и без VS Code: открыть PowerShell в нужной папке через Проводник. HTML-код при этом пишем в текстовом редакторе.

Пример строки в терминале:

PS C:\Users\Student\Documents\git-pet-site>

Это приглашение к вводу, его печатать не надо. Оно показывает, в какой папке сейчас работает терминал. После > вводим команду и нажимаем Enter.

git --version

Здесь git — имя программы, --version — просьба показать её версию. Ответ начинается с git version; цифры на разных компьютерах могут отличаться.

Если команд в примере несколько, выполняйте их по одной сверху вниз. Само слово powershell над блоком, кавычки оформления блока и строки ответа копировать не надо.

Три полезные команды PowerShell:

Команда Что делает
Get-Location Показывает текущую папку
Get-ChildItem Показывает её содержимое
cd "C:\Users\Student\Documents\git-pet-site" Переходит в указанную папку

В последней строке нужен ваш путь. Кавычки позволяют использовать путь с пробелами. Команды Git относятся к текущему проекту, поэтому сначала всегда проверяйте папку.

4. Установка и первая настройка

Если git --version работает, установка уже выполнена. Если PowerShell пишет, что git не найден, скачайте установщик с официальной страницы Git для Windows. На учебном компьютере установку может выполнять преподаватель.

При установке оставьте вариант, позволяющий запускать Git из командной строки и других программ. После установки полностью закройте и снова откройте терминал, а при необходимости и VS Code. Повторите git --version.

В примерах нужны Git 2.28 или новее: мы используем git init -b main, git switch и git restore.

Теперь создадим отдельную пустую папку git-pet-site внутри «Документов». Откроем её в редакторе и терминале. Не используйте для первого опыта папку всего курса или готового большого сайта.

git init -b main

init означает «начать репозиторий», а -b main задаёт имя первой ветки — main. Ветку разберём позже; сейчас это название нашей основной линии работы.

Репозиторий — хранилище проекта с его историей. В этой обычной рабочей папке Git создаст скрытую служебную папку .git. Вручную редактировать её не нужно: она хранит историю и настройки. Само создание репозитория ещё не сохраняет первый вариант сайта. Справка git init.

Представимся Git:

git config user.name "Student"
git config user.email "student@example.test"

Это подпись автора будущих сохранений. Здесь учебные имя и адрес; почтовый ящик создавать не нужно. Эти команды не регистрируют аккаунт и не выполняют вход на GitHub. Без --global настройка относится только к этому репозиторию — удобно на общем компьютере.

5. Самая важная картинка: стол, корзинка, альбом

Чтобы понять Git, представим три места:

РАБОЧАЯ ПАПКА              ПОДГОТОВКА                  ИСТОРИЯ
«стол с рисунками»         «корзинка для снимка»       «альбом со снимками»

редактируем файлы  --git add-->  выбираем изменения  --git commit-->  сохраняем версию

Рабочая папка — файлы, которые мы сейчас редактируем.

Область подготовки, или индекс, — то, что мы выбрали для следующего сохранения. Английское слово staged означает «подготовлено».

Коммит — сохранённое состояние проекта с подписью автора и сообщением о том, что сделано. Для начала удобно представлять его снимком. Git хранит содержимое файлов, а не фотографию экрана.

Коммит учитывает подготовленные изменения. Остальные уже сохранённые файлы остаются частью проекта. Новый файл, который мы ещё не добавили, сам в коммит не попадёт.

Зачем корзинка? Допустим, вы исправили заголовок и начали переделывать меню. Заголовок готов, меню ещё нет. Можно сохранить готовую часть отдельно.

Запомните: Ctrl+S сохраняет файл на диск. git add готовит его текущее содержимое. git commit записывает подготовленный результат в историю.

6. Первый коммит: от файла до сохранения

В редакторе создадим файл index.html, запишем код и нажмём Ctrl+S:

<!doctype html>
<html lang="ru">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>Мой питомец</title>
</head>
<body>
    <h1>Мой кот Барсик</h1>
    <p>Это первая версия моего сайта.</p>
</body>
</html>

Откроем файл в браузере двойным щелчком. Для этой страницы PHP, MySQL и OpenServer не нужны.

В терминале спросим Git, что происходит:

git status

Ожидаем Untracked files и index.html. Перевод: «Есть файл, который Git пока не отслеживает».

Подготовим его:

git add index.html
git status

Теперь файл находится в разделе Changes to be committed: «Изменения, готовые к коммиту». Если git add ничего не напечатал, это нормально; результат проверяем через status.

Запишем первый коммит:

git commit -m "Создать первую страницу о питомце"
git status

-m позволяет написать сообщение прямо в команде. Текст берём в обычные прямые кавычки "...".

После коммита ожидаем nothing to commit, working tree clean: «Новых изменений для коммита нет». Это не проверка качества сайта. Git только сообщает о состоянии файлов.

Проверка: появился ли сайт в интернете после коммита? Нет. Всё произошло на нашем компьютере.

7. Вторая версия и поиск отличий

В редакторе заменим строку заголовка:

<h1>Кот Барсик — хозяин дома</h1>

Сохраним файл. Затем:

git status
git diff

modified означает «изменён». diff показывает разницу. Среди служебных строк увидим примерно это:

-    <h1>Мой кот Барсик</h1>
+    <h1>Кот Барсик — хозяин дома</h1>

Минус обозначает старую строку, плюс — новую. Это способ показать изменения, а не символы, которые нужно вставлять в HTML.

Теперь подготовим и проверим именно будущий коммит:

git add index.html
git diff --staged
git commit -m "Уточнить заголовок страницы"
Команда Какой вопрос задаём
git status Какие файлы новые, изменённые и подготовленные?
git diff Чем рабочие файлы отличаются от подготовленного состояния?
git diff --staged Чем подготовленное состояние отличается от последнего коммита?

Обычный git diff не показывает содержимое новых неотслеживаемых файлов. Сначала посмотрите status, затем подготовьте нужный файл и используйте git diff --staged.

Если вывод занимает весь терминал и внизу стоит (END), нажмите английскую q: это выход из просмотра. Стрелки и пробел помогают прокручивать текст.

8. Почему иногда приходится делать add ещё раз

Представьте последовательность:

  1. Написали «Барсик любит спать», сохранили файл.
  2. Выполнили git add index.html.
  3. Передумали и написали «Барсик любит играть», снова сохранили файл.
  4. Выполнили git commit.

Что попадёт в коммит? Вариант про сон. Мы подготовили именно его. Последующее редактирование само не обновляет индекс. Чтобы включить вариант про игры, перед коммитом нужно ещё раз выполнить git add index.html. Справка git add.

Один файл может одновременно быть в разделах подготовленных и неподготовленных изменений. Это означает, что после add его снова редактировали.

Рабочая привычка:

Изменил → Ctrl+S → status → diff → add → diff --staged → commit

Не нужно учить все команды Git за один день. Сначала освойте этот круг.

9. Как посмотреть историю

git log --oneline

Пример вывода, у вас буквы и цифры будут другими:

8d1e2f3 (HEAD -> main) Уточнить заголовок страницы
1a2b3c4 Создать первую страницу о питомце

Самое новое сохранение сверху. Короткая последовательность букв и цифр — идентификатор коммита, его ещё называют хешем. Это адрес сохранения внутри истории.

main — текущая ветка. HEAD -> main показывает, что сейчас мы работаем в ней.

Чтобы посмотреть изменения последнего коммита:

git show

Для другого коммита после git show можно написать его настоящий идентификатор из своего log. Просмотр не меняет рабочие файлы.

Хорошее сообщение объясняет действие: «Добавить список любимых занятий». Сообщения «123», «правки» и «всё» мало помогают вспомнить, что произошло. Один коммит удобно посвящать одной законченной задаче.

10. Как отменить ошибку и не перепутать команды

Передумал включать файл в ближайший коммит

У нас уже есть хотя бы один коммит. Мы изменили файл и выполнили add, но хотим убрать изменение из подготовки:

git restore --staged index.html

Текст в рабочем файле останется. Мы только убрали изменение из будущего коммита. Проверьте git status и откройте файл.

Хочу выбросить пробное изменение в самом файле

Допустим, после коммита случайно испортили заголовок и ещё не делали add. Сначала посмотрим, что именно будет потеряно:

git diff -- index.html

Если точно хотим отказаться от этой правки:

git restore index.html

Эта команда заменяет содержимое рабочего файла версией из индекса. В нашем примере индекс совпадает с последним коммитом, поэтому возвращается сохранённый заголовок. Несохранённая в Git правка исчезнет; Git не гарантирует её восстановление. Для первого опыта используйте только специально добавленную ненужную строку.

Если до этого уже был add, источник восстановления может отличаться от последнего коммита. Поэтому нельзя считать restore универсальной кнопкой «вернуть всё». Справка git restore.

Для отмены уже сделанного коммита существует git revert: он создаёт новый коммит с обратными изменениями. Это отдельный приём; в первой лабораторной история не переписывается.

11. Что не должно попадать в историю

В папке сайта бывают полезные исходники и временные файлы. .gitignore — текстовый файл со списком того, что не нужно добавлять в Git.

Например:

notes-private.txt
*.log
.env

Здесь notes-private.txt — конкретное имя, *.log — файлы с окончанием .log, а .env часто используют для локальных настроек с секретами.

Сам .gitignore добавляем в коммит: правила нужны вместе с проектом. Он не удаляет файлы с компьютера и не скрывает их от других программ.

Уже отслеживаемый файл не перестаёт отслеживаться от добавления в .gitignore. Правила также не стирают старые коммиты. Поэтому настоящие пароли, ключи и личные данные не включаем в историю с самого начала. Справка .gitignore.

В лабораторной используем только вымышленные данные. Для PHP-проекта исходный код можно хранить в Git, а реальные пароли базы — в отдельной локальной конфигурации. Саму работающую базу MySQL Git автоматически не сохраняет.

12. Остановимся и проверим понимание

  1. Нажали Ctrl+S. Появился коммит?
  2. Сделали add, потом ещё раз поменяли файл. Какая версия подготовлена?
  3. git diff ничего не показал. Можно ли утверждать, что нет подготовленных изменений?
  4. Что делает git restore --staged index.html с текстом рабочего файла?
  5. Где хранится история локального проекта из нашего примера?

Ответы: 1 — нет; 2 — версия на момент add; 3 — нет, проверьте status и diff --staged; 4 — оставляет его на месте; 5 — в служебной папке .git.

Если эти ответы понятны, можно переходить к веткам. Если нет — ещё раз пройдите один цикл с изменением заголовка.

13. Ветка: место для отдельной идеи

Представьте, что рабочий сайт уже готов, а вы хотите попробовать новую страницу «О питомце».

Ветка — отдельная линия развития проекта. Она позволяет делать свои коммиты, пока основная ветка остаётся на прежней версии. Git не создаёт вторую папку рядом: при переключении ветки он обновляет файлы в той же рабочей папке.

Для нашего упражнения перед переключением обязательно сохраните работу коммитом и проверьте чистый git status. Незакоммиченные изменения не всегда принадлежат одной ветке: Git может перенести их при переключении или отказать, если они будут затёрты.

Создадим ветку и перейдём в неё:

git switch -c about-pet
git branch

-c означает «создать». Звёздочка в выводе git branch отмечает текущую ветку. Теперь новые коммиты будут появляться в about-pet. Справка git switch.

Создайте about.html, сохраните его и выполните:

git add about.html
git commit -m "Добавить страницу о питомце"
git switch main

Файл about.html исчезнет из рабочей папки: в main его пока нет. Он сохранён в коммите другой ветки. Если снова перейти в about-pet, файл вернётся.

После коммита в about-pet:

A — B       ← main
     \
      C     ← about-pet, здесь добавили about.html

14. Слияние: забираем готовую идею в main

Мы уже вернулись в main. Перенесём туда результат ветки:

git merge about-pet
git status

merge означает «объединить». Команда объединяет указанную ветку с текущей. Поэтому направление важно: сначала git switch main, затем git merge about-pet.

В этом опыте после ответвления мы не делали новых коммитов в main. Git обычно напишет Fast-forward: передвинет main к готовому коммиту. Отдельный коммит слияния здесь не нужен.

A — B — C   ← main, about-pet

Страница about.html теперь есть и в основной ветке. Ветка about-pet остаётся; само слияние её не удаляет. Справка git merge.

А если два человека поменяли одно место по-разному?

Иногда Git не может сам выбрать итоговый текст. Это конфликт слияния. В файле могут появиться метки:

<<<<<<< HEAD
<h1>Мой кот</h1>
=======
<h1>Наш любимый Барсик</h1>
>>>>>>> about-pet

Сверху вариант текущей ветки, снизу — присоединяемой. Человек выбирает итоговый текст, убирает метки и лишний вариант, проверяет страницу, делает git add исправленного файла и git commit -m "Разрешить конфликт заголовка".

Конфликт — просьба принять решение. В обязательном опыте лабораторной мы специально не меняем одну строку в двух ветках, поэтому конфликта быть не должно. Если он возник, сначала прочитайте git status вместе с преподавателем.

15. GitHub: что будет следующим шагом

До этого момента всё работало локально. Удалённый репозиторий — репозиторий по другому адресу, например на GitHub. Он нужен для обмена историей с другими людьми и хранения копии отправленных коммитов.

Слово Что означает
remote Настроенный адрес другого репозитория
origin Распространённое имя такого адреса
push Отправить коммиты в удалённый репозиторий
clone Получить локальную копию репозитория с историей
pull Получить изменения и попытаться включить их в текущую ветку

push не отправляет несохранённый текст редактора или неподготовленные файлы. Сначала нужны коммиты. pull может привести к конфликту; это не просто кнопка «скачать и всё заменить».

На первом занятии достаточно понимать направление:

наш компьютер  -- push -->  удалённый репозиторий
наш компьютер  <-- pull --  удалённый репозиторий

Размещение кода на GitHub само по себе не запускает PHP и MySQL. Публикация работающего сайта — отдельная задача. Основную лабораторную можно сдать без GitHub.

16. Шпаргалка для первого проекта

Что хочу сделать Команда
Начать историю в новой папке git init -b main
Узнать состояние файлов git status
Увидеть неподготовленные изменения git diff
Подготовить конкретный файл git add index.html
Проверить будущий коммит git diff --staged
Записать подготовленный результат git commit -m "Понятное описание"
Посмотреть историю git log --oneline
Убрать файл из подготовки, оставив правки git restore --staged index.html
Отбросить правки файла относительно индекса git restore index.html — сначала проверить, что теряете
Создать ветку и перейти в неё git switch -c about-pet
Вернуться в основную ветку git switch main
Объединить готовую ветку с текущей git merge about-pet

Встречается и git add .: точка означает текущую папку, команда подготавливает изменения в ней и её подпапках, включая удаления, с учётом правил игнорирования. В первой работе перечисляем конкретные файлы, чтобы видеть свой выбор.
