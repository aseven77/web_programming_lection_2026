Лабораторная работа №13

Роли и защита CRUD и API

Лекция №13 · Предыдущая работа: вход и выход

Что сделаем

Гости продолжат читать новости. Пользователи с ролью user смогут входить и смотреть профиль. Только admin сможет управлять новостями через формы №6 и API №7.

Работа состоит из двух частей: сначала защищаем обычные формы, затем ту же политику применяем к JSON API. Проверки второй части обязательны, если API из №7 находится в вашем проекте.

Перед началом

Нужны работающие №11–12, таблица news, admin.php из №6 и файлы №7: api-news.php, news-app.html, news-app.js. Для API можно использовать готовые версии из комплекта примеров, если вы ещё не собрали №7. Они реализуют чтение, добавление и удаление.

Сохраните резервную копию файлов вне обслуживаемой сервером папки. В дальнейшем заменяем существующие обработчики по прежним адресам. Не оставляйте рядом работающие admin-old.php или старый API: они сохранят обход ограничений.

Шаг 1. Подготовить две учётные записи

Через register.php создайте reader@example.test и editor@example.test. Используйте вымышленные имена и учебные пароли. Пока обе записи должны иметь role=user.

В phpMyAdmin выберите базу site, проверьте записи:

SELECT id, name, email, role
FROM users
WHERE email IN ('reader@example.test', 'editor@example.test');

Назначьте второму пользователю административную роль:

UPDATE users SET role = 'admin'
WHERE email = 'editor@example.test';

Маленькая проверка: изменена ровно одна нужная строка. Повторите SELECT. Пароли и хеши не меняйте. Этот SQL выполняет владелец учебной базы, не посетитель сайта.

Шаг 2. Создать проверку администратора

Создайте полный файл access.php: 

<?php
require_once __DIR__ . '/auth.php';

function auth_require_admin(): array {
    $user = auth_require_user();
    if ($user['role'] !== 'admin') {
        http_response_code(403);
        exit('Недостаточно прав. Управление новостями доступно администратору.');
    }
    return $user;
}

Сначала проверяем факт входа. Затем точное значение роли. Гость получает переход на форму входа, вошедший пользователь без прав — 403. Неизвестная роль тоже запрещена.

Шаг 3. Защитить начало admin.php

В существующем admin.php замените строку подключения config.php на: 

require_once __DIR__ . '/access.php';
auth_require_admin();

Эти строки должны идти сразу после <?php, до $errors, обработки POST и SQL. Подключение к базе уже выполнит цепочка access.php → auth.php → bootstrap.php → config.php.

Остальные функции из №6 (e, positiveId, findNews) оставьте. Наши функции имеют префикс auth_, поэтому конфликта имён нет.

Маленькая проверка: гостем откройте admin.php — ожидайте вход. Войдите как reader@example.test — ожидайте 403. Как editor@example.test — страницу управления.

Шаг 4. Защитить все POST-формы администратора

В начало существующей POST-ветки добавьте проверку токена, до чтения $action: 

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    auth_check_post();
    // Далее существующий код чтения action и обработки CRUD.

Это начало существующего блока, а не новая ветка рядом со старой. Вторую открывающую фигурную скобку не добавляйте.

Внутрь каждой формы method="post" добавьте: 

<input type="hidden" name="csrf" value="<?= auth_e(auth_csrf()) ?>">

Поле нужно и общей форме добавления/редактирования, и форме удаления внутри цикла. Ссылку GET для открытия редактирования менять не нужно: она только читает данные, а сохранение выполняет POST.

Маленькая проверка: администратор добавляет, редактирует и удаляет тестовую новость. Затем удалите скрытый токен через DevTools и повторите действие — 403, база не меняется. Обновите страницу после опыта.

Полный admin.php для сверки содержит те же изменения. Его можно скопировать целиком вместо ручного редактирования, если ваш исходный файл совпадал с №6.

Шаг 5. Изменить API

Откройте api-news.php из №7. Внутри try замените подключение config.php на: 

require_once __DIR__ . '/auth.php';
header('Cache-Control: no-store');
$currentUser = auth_user();

Заголовок JSON и функция reply() из №7 остаются. API не должен вызывать auth_require_user(): эта функция перенаправляет HTML-страницы, а здесь нужен JSON с кодом ответа.

В GET-ветке замените старый reply(['news' => $news]); на:

reply([
    'news' => $news,
    'csrf' => $currentUser !== null && $currentUser['role'] === 'admin'
        ? auth_csrf() : null,
]);

Всем доступен список, но токен для административных операций выдаём только администратору. Ответ не кешируем, так как он зависит от сессии.

После проверки допустимого метода, но перед проверкой Content-Type, разбором JSON и всеми SQL-изменениями, вставьте: 

if ($currentUser === null) {
    reply(['error' => 'Сначала войдите в систему.'], 401);
}
if ($currentUser['role'] !== 'admin') {
    reply(['error' => 'Недостаточно прав.'], 403);
}
if (!auth_valid_csrf($_SERVER['HTTP_X_CSRF_TOKEN'] ?? null)) {
    reply(['error' => 'Обновите список и повторите действие: неверный токен.'], 403);
}

Существующие проверки JSON, заголовка, текста, id, параметры PDO и обработку исключений сохраняем. Иначе новая защита случайно уберёт уже изученную проверку данных.

Полный api-news.php для сверки входит в комплект.

Шаг 6. Научить JavaScript передавать токен

В news-app.js перед функцией request() добавьте:

let csrfToken = '';

В функции request() замените создание options на:

const options = payload === undefined ? {} : {
    method: 'POST',
    headers: {
        'Content-Type': 'application/json',
        'X-CSRF-Token': csrfToken
    },
    body: JSON.stringify(payload)
};

В loadNews() сразу после const data = await request(); добавьте: 

csrfToken = typeof data.csrf === 'string' ? data.csrf : '';

Теперь начальная загрузка и кнопка обновления получают актуальный токен. После входа в другой вкладке нажмите «Обновить список». После смены пользователя прежний токен будет отклонён сервером.

В news-app.html под заголовком можно добавить навигацию и пояснение:

<p><a href="login.php">Войти</a> · <a href="profile.php">Мой профиль</a></p>
<p>Читать новости могут все. Добавление и удаление доступны администратору. После входа обновите список.</p>

Формы и кнопки в учебном API-интерфейсе остаются видимыми, чтобы проверить серверный отказ. Их скрытие по роли — самостоятельное улучшение интерфейса, не замена проверкам.

Готовые news-app.js и news-app.html содержат эти изменения. Открывайте страницу через тот же origin, что и вход, а не как локальный HTML-файл.

Шаг 7. Матрица доступа

Создайте одну временную новость администратором. Её id используйте в опытах ниже. Для каждого запрещённого действия проверяйте, что новость осталась и число строк не изменилось.

Проверка Гость user admin
GET api-news.php 200, список 200, список 200, список и токен
GET profile.php 303 на вход 200 200
GET admin.php 303 на вход 403 200
POST API create/delete с подходящим токеном, если он доступен 401 403 201/200
POST API без токена 401 403 403
POST формы admin без токена 303 на вход 403 403

В старом интерфейсе №7 нажмите «Добавить» обычным пользователем. JavaScript должен показать сообщение из JSON, а не ошибку разбора HTML. Прямой запрос тоже обязан получить отказ.

Для проверки прямого запроса откройте Console на своём локальном сайте, будучи гостем или обычным пользователем: 

fetch('api-news.php', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ action: 'create', title: 'Запрещённая попытка', content: 'Проверка' })
}).then(async response => console.log(response.status, await response.json()));

Ожидайте 401 для гостя, 403 для пользователя и отсутствие новой записи. Проверять только текст уведомления недостаточно.

Шаг 8. Проверить смену роли

Будучи администратором, откройте admin.php. В phpMyAdmin выполните:

UPDATE users SET role = 'user'
WHERE email = 'editor@example.test';

Обновите admin.php — теперь 403. Отправьте действие из ранее открытого API-интерфейса — тоже 403. Повторный вход не требуется, потому что роль читается из базы для каждого запроса.

Для завершения работы верните admin только этой учебной записи и повторите успешное создание и удаление. Не меняйте роль всех пользователей запросом без WHERE.

Типичные ошибки

Симптом Что проверить
Кнопки скрыты, но прямой POST проходит Проверка должна быть в PHP-обработчике
Администратор добавляет, но не может удалить Поле CSRF забыто в форме удаления
fetch сообщает «сервер вернул не JSON» В API использован HTML-редирект либо есть предупреждение PHP перед JSON
После входа API отвечает ошибкой токена Обновить список; проверить X-CSRF-Token в Network
Роль сменена, но доступ остаётся Не брать роль только из сессии; читать актуальную запись
Через старый адрес запись всё ещё меняется Удалить из обслуживаемой папки старый незащищённый обработчик, сохранив резервную копию вне неё

Самостоятельная работа

  1. Добавьте в профиль ссылку на admin.php только для роли admin. Серверную проверку сохраните.
  2. Скрывайте формы изменения в интерфейсе API для посетителя без административного токена. После этого повторите прямой запрос из консоли: он по-прежнему должен быть запрещён.
  3. Со звёздочкой: опишите, какие изменения понадобятся для правила «автор редактирует только свою новость». Не смешивайте роль и принадлежность записи.

Что сдать и критерии

Сдайте access.php, изменённые admin.php, api-news.php, news-app.js, news-app.html и общие файлы №11–12. Приложите матрицу результатов с HTTP-кодами и подтверждением, что запрещённые операции не меняют базу.

Работа выполнена, если публичное чтение осталось доступным, профиль требует входа, формы и API разрешают изменения только администратору с правильным CSRF-токеном, а изменение роли учитывается в следующем запросе.
